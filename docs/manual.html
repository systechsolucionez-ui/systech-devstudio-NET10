1Qué es SYSTECH Studio

Es tu taller para trabajos remotos de backend. Le das al agente un pedido en texto y, si querés, el proyecto del cliente en un .zip. El agente escribe el código, lo verifica dos veces y te lo devuelve listo para mandar.

1 · PedidoTexto y archivos del cliente
→
2 · AgenteGenera o modifica el código
→
3 · Verificación 1Compila, tests, vulnerabilidades, secretos
→
4 · Verificación 2Entorno limpio y revisor independiente
→
5 · VosRevisás, aprobás y entregás el .zip

Si algo falla en las verificaciones, el agente corrige solo y vuelve a verificar. Vos solo intervenís al final, o cuando el agente no logra resolverlo.

Dos modos de uso
  • Demostración (--demo): un agente simulado que no gasta nada. Sirve para aprender a usar las pantallas.
  • Real: el agente de verdad, que usa tu API key (o tu suscripción de Claude) y genera código .NET real.

2Instalación

El Studio corre dentro de un GitHub Codespace: una computadora en la nube con VS Code en el navegador. Tu PC solo se usa para ver la pantalla. El repositorio trae un .devcontainer que deja todo instalado: Node.js, .NET 10 (LTS), Docker, las dependencias y Claude Code.

  1. Tené tu copia del repositorioHacé un fork del repositorio de SYSTECH Studio en tu cuenta de GitHub, o usalo directo si es tuyo.
  2. Cargá la API keyAntes de crear el Codespace, configurá el secreto ANTHROPIC_API_KEY (sección 4). Si te lo salteás, GitHub te lo pide al crear el Codespace.
  3. Creá el CodespaceEn tu repositorio: botón verde <> Code → pestaña Codespaces → Create codespace on main. La primera vez tarda unos minutos mientras instala todo.
  4. Abrí la terminalAparece abajo sola. Si no, menú ☰ → Terminal → New Terminal. Ya está ubicada en la carpeta del Studio.
QuéDónde
El programa del StudioLa carpeta del repositorio: /workspaces/<nombre-del-repo>
Los trabajos (código, registros, .zip de entrega)~/systech-jobs, fuera del repositorio: nunca se suben a GitHub.
La terminal correcta

Todos los comandos de este manual van en la terminal del Codespace, abajo en la pantalla de VS Code del navegador. El renglón empieza con @tu-usuario ➜ /workspaces/.... Si ves MINGW64 o PS C:\, estás en una terminal de tu PC y los comandos no van a funcionar.

Volver a abrir el Codespace

Entrá a github.com/codespaces y hacé clic en el tuyo. No crees uno nuevo cada vez: los trabajos guardados quedan en el que ya tenés.

3Prender y apagar el Studio

En la terminal del Codespace, desde la carpeta del repositorio:

Modo demostración (sin gastar)

bash scripts/start.sh --demo

Usa un agente simulado que recorre el ciclo completo: la verificación 1 falla, el agente corrige, la verificación 2 encuentra un problema, el agente corrige otra vez y finalmente se aprueba. Ideal para aprender las pantallas.

Con el agente real

bash scripts/start.sh

Antes, configurá la API key (sección 4). Al arrancar, la terminal muestra el encabezado de SYSTECH Studio con la versión.

Abrir la pantalla del Studio

  1. Esperá el mensajeEn la terminal tiene que aparecer SYSTECH Studio escuchando en http://127.0.0.1:5080.
  2. Pestaña PORTSAbajo, al lado de TERMINAL, abrí PORTS y buscá el puerto 5080. Si no aparece, tocá Add Port y escribí 5080.
  3. Abrir en el navegadorPasá el mouse sobre la dirección del 5080 y tocá el globo 🌐 (Open in Browser). Podés guardar esa pestaña en favoritos.
La visibilidad del puerto siempre en Private

En la columna Visibility del puerto 5080 tiene que decir Private. Así solo vos, con tu cuenta de GitHub, podés entrar. Nunca lo cambies a Public: el Studio no tiene contraseña propia.

Apagarlo

En la terminal donde está corriendo, apretá Ctrl + C. Si cerrás esa terminal, también se apaga.

Mientras está prendido

La terminal queda "ocupada" y no vuelve a aparecer el $. Es normal. Si necesitás escribir otros comandos, abrí otra terminal con el + del panel de terminales.

Cuando el Codespace se duerme

Si no lo usás durante un rato (por defecto, 30 minutos), GitHub detiene el Codespace y el Studio se apaga con él. Tus trabajos no se pierden. Al volver:

  1. Abrí el Codespace de nuevo (sección 2).
  2. Ejecutá bash scripts/start.sh.
  3. Si un trabajo estaba a mitad de camino, va a aparecer como Interrumpido. Abrilo y tocá Reintentar verificación.

Opción A · Paso a paso con API key

Parte 1 · Crear la clave

  1. Entrá a la consolaAbrí platform.claude.com e iniciá sesión, o creá una cuenta.
  2. Cargá créditos y poné un límiteEn la sección de facturación (Billing), cargá saldo y configurá un límite de gasto mensual. Es tu red de seguridad.
  3. Creá la claveEntrá a platform.claude.com/settings/keys → Create key. Ponele un nombre claro, por ejemplo systech-studio-codespace.
  4. Copiala en ese momentoLa clave empieza con sk-ant- y se muestra una sola vez. Copiala y pasá directo a la parte 2. Si la perdés, borrala y creá otra.

Parte 2 · Guardarla como secreto de Codespaces (el lugar correcto)

  1. Abrí tu configuración de GitHubEn github.com, tocá tu foto de perfil (arriba a la derecha) → Settings.
  2. Sección CodespacesEn la barra izquierda, dentro de Code, planning, and automation, entrá a Codespaces.
  3. Nuevo secretoJunto a Codespaces secrets, tocá New secret.
  4. Completá los datos
    • Name: ANTHROPIC_API_KEY (exactamente así, en mayúsculas).
    • Value: pegá la clave sk-ant-....
    • Repository access: elegí tu copia del repositorio de SYSTECH Studio.
    Tocá Add secret.
  5. Reiniciá el Codespace si ya existíaUn Codespace que ya estaba creado no ve el secreto nuevo. En github.com/codespaces, tocá ⋯ → Stop codespace y después abrilo de nuevo.
  6. Comprobá que llegóEn la terminal del Codespace ejecutá el comando de abajo. Muestra si la clave está cargada sin imprimirla.
[ -n "$ANTHROPIC_API_KEY" ] && echo "API key cargada" || echo "Falta la API key"
  1. Prendé el Studio en modo realbash scripts/start.sh
  2. Mirá el panel EntornoEn la barra izquierda del Studio, abajo, tiene que decir API key configurada con un punto verde.
Nunca pongas la API key en estos lugares
  • En un archivo del proyecto (.env, appsettings.json, código).
  • En el texto de un pedido del Studio.
  • En un chat, un mail, un issue o una captura de pantalla.
  • En un comando de la terminal, porque queda en el historial.

Si sospechás que se filtró, borrala en la consola y creá otra. Después actualizá el secreto en GitHub.

Opción B · Con tu suscripción de Claude

  1. Iniciá sesión una vezEn la terminal del Codespace, con el Studio apagado, escribí claude y apretá Enter.
  2. Seguí las instruccionesElegí iniciar sesión con tu cuenta. Se abre una página en el navegador para autorizar. Al terminar, escribí /exit.
  3. Prendé el Studiobash scripts/start.sh. El panel Entorno va a decir Sesión de Claude iniciada.
Si tenés las dos

Si el secreto ANTHROPIC_API_KEY existe, el agente usa la API key, aunque también hayas iniciado sesión.

5Pantalla 1 · Nuevo trabajo

Acá cargás lo que te pide el cliente.

Nombre del trabajo
Un título corto para reconocerlo. También se usa para el nombre del .zip. Ej.: Saga de pagos para la API de pedidos.
Qué tiene que hacer el agente
El pedido completo, en lenguaje natural: cuanto más claro, mejor resultado (ver sección 11). Se guarda solo como borrador en tu navegador mientras escribís.
Archivos (opcional)
Arrastralos al recuadro punteado o hacé clic para elegirlos. Hasta 20 archivos y 300 MB en total.
  • Un .zip es el proyecto sobre el que trabaja el agente: lo descomprime y lo modifica. Si el zip trae una sola carpeta adentro, la "aplana" automáticamente.
  • Otros archivos (PDF, Word, imágenes, ejemplos) quedan como material de referencia. El agente los lee, pero no se incluyen en la entrega.
  • Sin archivos, el agente crea el proyecto desde cero.
Intentos de corrección automática (1 a 5)
Cuántas veces puede el agente corregir y volver a verificar solo, antes de pedirte que intervengas. 3 es un buen equilibrio. Más intentos dan más chances de que salga solo, pero también más gasto.
Incluir prueba de humo con Docker
Levanta los contenedores del proyecto y corre scripts/smoke-test.sh. Solo sirve si el proyecto tiene docker-compose.yml y ese script. Tarda varios minutos más.

Tocá Generar y verificar. El Studio sube los archivos y te lleva al Taller.

A la derecha ves los Trabajos recientes (clic para abrirlos) y un resumen de cómo trabaja el agente.

6Pantalla 2 · Taller

En todas las pantallas

Abajo se ve siempre la firma SYSTECH Studio v1.1.0 · Creado por José Antonio Vivas · Systech Soluciones. En la barra lateral, Acerca de muestra la versión, el autor, la licencia, el enlace al repositorio y el aviso de privacidad.

Es donde mirás el trabajo en vivo, revisás el código y corregís errores. Se actualiza solo cada 2 segundos mientras el trabajo está en curso.

Encabezado y estado

Arriba ves el nombre, el estado, cuándo empezó y cuánto lleva gastado el agente. Estos son los estados posibles:

EstadoQué significaQué hacés
En colaEspera a que termine otro trabajo. Se procesan de a uno.Esperar.
GenerandoEl agente está escribiendo el código.Mirar la consola si querés.
Verificación 1 / 2Se está verificando. Muestra "intento X de Y".Esperar.
CorrigiendoUna verificación falló y el agente está arreglándolo.Esperar.
Listo para tu revisiónPasaron las dos verificaciones.Revisar el código y aprobar.
Necesita tu atenciónSe acabaron los intentos y quedan errores.Corregir con el agente o pedir un cambio.
FallóNo se pudo seguir (p. ej. falta la API key o el zip es inválido). El motivo aparece en un recuadro rojo.Resolver el motivo y Reintentar.
InterrumpidoEl Studio o el Codespace se apagó a mitad de camino.Reintentar verificación.
CanceladoLo frenaste vos.Reintentar si querés seguir.

Botones del encabezado: Cancelar (mientras corre), Reintentar verificación (si se frenó o quedó con errores) y Ver entrega (cuando ya hay entrega).

La barra de progreso

Son cinco pasos: Pedido recibido → Código generado → Verificación 1 → Verificación 2 → Tu revisión. El paso actual se marca en dorado, los completos con ✓ y los que tienen problemas con ! en rojo.

Archivos y código

A la izquierda está la lista de Cambios respecto de lo que subiste. La letra al lado de cada archivo indica qué pasó con él:

  • A: archivo nuevo.
  • M: archivo modificado.
  • D: archivo borrado.

Hacé clic en uno para ver su contenido con números de línea. Cuando un error apunta a una línea, el botón Ver en el código te lleva ahí y la marca en rojo.

Panel Doble verificación

Muestra el resultado de cada chequeo (detalle en la sección 7). Debajo aparece Errores a corregir, con tres botones por cada error:

  • Corregir con el agente: el agente arregla solo ese error y se repiten las dos verificaciones.
  • Ver detalle: muestra el mensaje completo (por ejemplo, el error del compilador o el test que falló).
  • Ver en el código: abre el archivo en la línea del problema.

Si hay varios errores, aparece además Corregir todos. Las sugerencias menores del revisor están en un desplegable: no bloquean la entrega, pero conviene leerlas.

Consola del agente y registros

La consola muestra en vivo lo que hace el agente: archivos que escribe, comandos que corre y mensajes. Las claves secretas se ocultan automáticamente.

En Registros completos están los logs de cada paso: compilación, tests, revisor, etc. Se abren en otra pestaña. Sus nombres siguen el formato c1-a2-v1-test.log, que se lee ciclo 1, intento 2, verificación 1, tests.

Pedir un cambio

Escribí lo que querés ajustar (ej.: "que el plazo para pagar sea configurable desde appsettings") y tocá Enviar al agente. El agente aplica el cambio y se repiten las dos verificaciones. La entrega anterior queda anulada hasta que pase todo de nuevo.

Aprobar y preparar entrega

Este botón solo se habilita cuando las dos verificaciones están aprobadas. Al tocarlo, el trabajo pasa a Entregado y vas a la pantalla de Entrega.

Antes de aprobar, revisá vos también

Las verificaciones son muy buenas detectando errores, pero vos conocés al cliente. Leé el ENTREGA.md, mirá los archivos clave y las sugerencias menores. Si algo no te convence, pedí un cambio.

7La doble verificación, en detalle

Verificación 1 · automática: "¿funciona?"

ChequeoQué haceCuándo bloquea
Compilacióndotnet build en modo Release.Si hay errores de compilación. Las advertencias se informan, pero no bloquean.
Testsdotnet test de todos los proyectos de prueba.Si falla algún test. Si no hay tests, se marca como Aviso.
Paquetes vulnerablesdotnet list package --vulnerable, incluyendo dependencias indirectas.Severidad alta o crítica. Las medias y bajas son Aviso.
SecretosBusca claves reales en el código: Anthropic, GitHub, AWS, Mercado Pago, Stripe, claves privadas, etc.Si encuentra una. Una contraseña en appsettings.json fuera de desarrollo es Aviso.
Prueba de humo (opcional)Levanta Docker y corre scripts/smoke-test.sh. Al terminar borra los contenedores.Si el script falla o los contenedores no levantan.

Si la compilación falla, los demás chequeos no se ejecutan: primero tiene que compilar.

Verificación 2 · independiente: "¿es lo que se pidió, y está bien hecho?"

  1. Entorno limpioSe arma el .zip exactamente como lo recibiría el cliente, se descomprime en una carpeta nueva y se compila y testea desde cero. Así se detecta lo que "anda en mi máquina" pero no en otra, como archivos que faltan en el zip.
  2. Revisor independienteUn segundo agente, que no vio cómo se generó el código y solo puede leer, compara el resultado con tu pedido. Revisa cuatro áreas:
    • Pedido: ¿se cumple cada requisito?
    • Casos borde: concurrencia, reintentos, caídas de la base o de servicios externos.
    • Seguridad: OWASP, BOLA, validación de entradas, datos sensibles en logs.
    • Calidad: arquitectura y tests faltantes.

Cada hallazgo del revisor tiene una severidad:

SeveridadEjemplo¿Bloquea?
CríticaCobro duplicado, vulnerabilidad explotable, requisito no cumplido.Sí
AltaError probable en producción, falta test de un camino crítico.Sí
MediaMejora recomendable.No, se informa
BajaDetalle de estilo o documentación.No, se informa

Si el entorno limpio falla, el revisor no se ejecuta. Así no se gasta en revisar algo que no compila.

La regla de oro

Si falla cualquiera de las dos verificaciones, el agente corrige y se repiten ambas. Solo cuando las dos pasan en el mismo intento se arma la entrega.

8Pantalla 3 · Entrega

Resume las dos verificaciones, muestra el informe para el cliente y te da tres formas de enviar el trabajo.

Descargar .zip

Baja el trabajo a tu PC, listo para mandar por mail, WeTransfer o la plataforma del cliente. El zip incluye:

  • El código fuente y los tests.
  • ENTREGA.md: el informe que escribe el agente para el cliente (qué se hizo, cómo probarlo, decisiones y pendientes).
  • verificacion.md: los resultados de las dos verificaciones.
  • revision-independiente.md: el informe completo del revisor.
  • SHA256SUMS.txt: la huella SHA-256 de cada archivo del código.

Los tres informes terminan con la firma "Verificado con SYSTECH Studio v1.1.0 — Systech Soluciones", la fecha y la huella del contenido.

Y nunca incluye: .env, bin/, obj/, .git/, node_modules/, certificados (.pfx, .p12) ni tus archivos de referencia.

Subir a GitHub en una rama nueva

Escribí el repositorio como usuario/repositorio y, si querés, el nombre de la rama (si lo dejás vacío se genera solo, tipo systech/saga-de-pagos-abc123). Se sube exactamente el contenido del zip.

Permisos de GitHub

Desde el Codespace, el token automático solo puede escribir en el repositorio del propio Codespace. Para subir al repositorio de un cliente, ejecutá una vez gh auth login en una terminal del Codespace y seguí las instrucciones.

Copiar informe para el cliente

Copia el texto de ENTREGA.md (con la firma) y la huella SHA-256 del .zip al portapapeles, para pegarlo en el mail o mensaje con el que mandás el trabajo.

Huellas: cómo comprueba el cliente que nada cambió

Hay dos huellas distintas:

  • Huella del .zip: se ve en la pantalla de Entrega, va en el informe copiado y se descarga como archivo .sha256. No puede ir adentro del propio zip, porque cambiaría al agregarla. Si el cliente obtiene la misma, el archivo llegó idéntico.
  • Huella del contenido: va en la firma de los informes y en SHA256SUMS.txt. Sirve para comprobar archivo por archivo, aunque alguien vuelva a comprimir el proyecto.
# Linux / macOS: huella del .zip
sha256sum mi-trabajo.zip

# Windows (PowerShell): huella del .zip
Get-FileHash mi-trabajo.zip -Algorithm SHA256

# Después de descomprimir: comprobar cada archivo
sha256sum -c SHA256SUMS.txt

9Entregas e Historial

  • Entregas: solo los trabajos con doble verificación aprobada. Desde acá podés volver a descargar cualquier zip.
  • Historial: todos los trabajos, con su estado, fecha y costo. Clic en el nombre para abrirlo.

Los trabajos se guardan en el Codespace (~/systech-jobs) y sobreviven a reinicios. Si borrás el Codespace, se pierden. Por eso, descargá siempre el zip de lo que entregás.

10Flujo recomendado para un trabajo remoto

  1. Recibí el pedido del clientePedile el proyecto en .zip (o el acceso al repositorio) y los requisitos por escrito.
  2. Prendé el Codespace y el StudioModo real: bash scripts/start.sh.
  3. Cargá el trabajoNombre, pedido bien escrito (sección 11), el zip y los documentos. Dejá 3 intentos.
  4. Dejalo trabajarPodés cerrar la pestaña del Studio: el trabajo sigue en el Codespace. Volvé en un rato. Ojo: si el Codespace se duerme por inactividad, el trabajo queda Interrumpido.
  5. Revisá en el TallerLeé los archivos clave, las sugerencias menores y el ENTREGA.md. Pedí cambios si hace falta.
  6. Aprobá y descargá el zipO subilo a una rama del repositorio del cliente.
  7. MandaloAdjuntá el zip y pegá el informe con Copiar informe. El cliente recibe también la evidencia de verificación.

Checklist antes de enviar

  • Las dos verificaciones están aprobadas.
  • Leí el ENTREGA.md y es correcto lo que dice.
  • Revisé las sugerencias menores y decidí qué hacer con ellas.
  • El zip no tiene datos del cliente que no deban viajar (ej. bases de datos de prueba con datos reales).
  • El nombre del zip y del trabajo son claros para el cliente.

11Cómo escribir un buen pedido

El agente es tan bueno como el pedido. Un buen pedido dice qué construir, las reglas de negocio, las restricciones y cómo saber que está bien.

Plantilla

Objetivo: [qué tiene que lograr, en una frase]

Contexto: [proyecto, tecnología, qué ya existe]

Requisitos:
1. [requisito concreto y verificable]
2. [...]

Reglas de negocio:
- [ej.: una orden no pagada en 30 minutos se cancela y libera stock]

Restricciones:
- [ej.: .NET 10, sin paquetes comerciales, sin cambiar la API pública]

Seguridad:
- [ej.: solo el dueño de la orden puede pagarla; validar montos]

Criterios de aceptación:
- [ej.: tests que prueben que un reintento no cobra dos veces]

Ejemplo real

Objetivo: agregar una saga de pagos a la API de pedidos adjunta.

Contexto: es el proyecto .NET 10 con Clean Architecture, MediatR,
EF Core con PostgreSQL y outbox.

Requisitos:
1. Al crearse una orden, cobrarla con un IPaymentGateway (interfaz,
   con una implementación falsa para tests).
2. Si el pago se aprueba, marcar la orden como pagada.
3. Si se rechaza, cancelarla y liberar el stock reservado.
4. Si no se paga en un plazo configurable (por defecto 30 min),
   cancelarla y liberar stock.

Seguridad:
- El cobro tiene que ser idempotente: un reintento nunca cobra dos veces.
- No loguear datos de tarjetas.

Criterios de aceptación:
- Tests de reintento, rechazo y vencimiento.
- La prueba de humo sigue pasando.
Consejos
  • Un pedido grande sale mejor dividido en varios trabajos chicos.
  • Si el cliente mandó un documento, adjuntalo, pero resumí en el pedido lo más importante.
  • Decí lo que no hay que tocar.
  • Escribí los criterios de aceptación: el revisor los usa para controlar.

12Costos y control de gasto

Con API key, cada ejecución del agente consume créditos. Cuentan como ejecución: generar, cada corrección y cada revisión. El Studio te muestra el costo acumulado de cada trabajo (Costo del agente: US$ …) en el Taller, la Entrega y el Historial.

ControlDóndePara qué
Tope por ejecuciónVariable STUDIO_MAX_BUDGET_USD (por defecto US$ 5)Ninguna ejecución individual puede gastar más que eso.
Intentos de correcciónAl crear cada trabajo (1 a 5)Limita cuántas veces corrige solo.
Límite mensualConsola de Claude, sección de facturación o límitesTu red de seguridad general.
ModeloVariable STUDIO_CLAUDE_MODEL (ej. sonnet u opus)Los modelos más grandes razonan mejor y cuestan más.

Para cambiar una variable, prendé el Studio con la variable adelante. Por ejemplo:

STUDIO_MAX_BUDGET_USD=3 STUDIO_CLAUDE_MODEL=sonnet bash scripts/start.sh
Para gastar menos
  • Usá --demo para practicar.
  • Escribí pedidos claros: menos idas y vueltas significan menos correcciones.
  • Dividí trabajos grandes.
  • Para tareas simples, usá STUDIO_CLAUDE_MODEL=sonnet.

13Seguridad

Lo que el Studio ya hace por vos

  • Acceso privado. Solo escucha dentro del Codespace, y entrás por el puerto Private de GitHub con tu cuenta.
  • Zips seguros. Rechaza archivos con rutas que escapan de la carpeta (zip slip), ignora enlaces simbólicos y frena zips gigantes (zip bomb).
  • Secretos aislados. La compilación y los tests corren sin tu API key y sin tu token de GitHub. El agente recibe solo la API key, y solo la subida a GitHub recibe el token.
  • Agente limitado. Puede editar archivos y usar dotnet dentro de la carpeta del trabajo. No tiene internet ni puede hacer git push.
  • Revisor de solo lectura. No puede modificar lo que revisa.
  • Entrega limpia. El zip nunca incluye .env, certificados ni carpetas de compilación, y la verificación 1 busca claves filtradas.
  • Interfaz protegida. Tiene protecciones contra CSRF, DNS rebinding y XSS.
  • Sin telemetría. El Studio no envía datos a Systech Soluciones ni a ningún otro servidor, y no carga nada de internet: las tipografías vienen incluidas.

Lo que te toca a vos

  • Puerto 5080 siempre en Private.
  • API key solo como secreto de Codespaces, con límite de gasto en la consola.
  • Procesá proyectos de clientes en los que confíes: sus tests se ejecutan en tu Codespace.
  • Leé lo que entregás. El agente y el revisor ayudan, pero la responsabilidad final es tuya.
  • No compartas capturas que muestren datos sensibles del cliente.

16Glosario

Agente
La IA que escribe y corrige el código (Claude Code, en modo automático).
Revisor independiente
Un segundo agente, de solo lectura, que audita el resultado sin haber participado en generarlo.
Codespace
Una computadora en la nube de GitHub con VS Code en el navegador. Ahí corre el Studio.
API key
Clave secreta que identifica tu cuenta de la consola de Claude y permite usar (y cobrar) el agente.
Secreto de Codespaces
Un valor privado que GitHub inyecta en tu Codespace como variable de entorno, sin que quede escrito en ningún archivo.
Ciclo e intento
Un ciclo empieza cada vez que creás el trabajo, pedís un cambio o tocás "Corregir". Dentro de cada ciclo, cada intento es una ronda de verificación 1 + 2.
Entorno limpio
Una carpeta nueva donde se descomprime el zip final para probarlo desde cero.
Prueba de humo
Una prueba rápida de punta a punta con el sistema levantado en Docker.
BOLA
Broken Object Level Authorization: que un usuario pueda ver o modificar datos de otro cambiando un ID.
OWASP Top 10
La lista de referencia de los riesgos de seguridad web más comunes.
Zip slip / zip bomb
Ataques con archivos zip: escribir fuera de la carpeta destino, o descomprimir a un tamaño gigantesco.
